# OpenAPI schema policy

ITAMbox tracks the REST API schema and the current `drf-spectacular`
diagnostics as reviewed artifacts. CI fails closed when schema generation is
unstable, the tracked schema changes, or diagnostic debt changes without an
explicit baseline update.

## Run the gate

From the repository root:

```bash
make openapi-check
```

The command requires `PYTHONHASHSEED=0` before Python starts. The Make target
sets it correctly. The gate uses development settings and a fixed,
non-production secret key used only for schema generation. It also empties
`PYTHONPATH`; an ambient import path would make dependency and settings
fingerprints untrustworthy, so direct invocations with a non-empty value fail.

A successful run proves all of the following:

1. Two isolated `manage.py spectacular --validate` processes generated
   byte-identical LF-only YAML.
2. The generated bytes exactly match `itambox/schema.yaml`.
3. Every warning and error has a portable identity in
   `scripts/openapi_diagnostics_baseline.json`.
4. The baseline is bound to Python 3.12, Django, Django REST framework,
   drf-spectacular, PyYAML, relevant Django settings, and the generation policy.

The checked-in schema is the reviewable API contract. Runtime Swagger and ReDoc
remain generated from the deployed revision.

## Diagnostic identities

A diagnostic identity contains:

- severity (`warning` or `error`);
- repository-relative source location, or a stable external-module marker;
- drf-spectacular breadcrumb;
- normalized message.

Source line numbers and path separators are removed because they are not part of
the diagnostic itself. Repository-root and Windows absolute paths, terminal escape sequences,
unexpected stderr, malformed summaries, and unknown diagnostic formats fail
the gate instead of being silently discarded. General POSIX route-like text is
retained because API paths such as `/api/assets/` are legitimate diagnostics.

Occurrence totals are published in `openapi-diagnostics.generated.json` for
investigation, but are deliberately absent from the baseline. A high occurrence
count therefore cannot create headroom for a different warning. Policy compares
the exact set of identities:

- a new identity fails;
- a disappeared identity also fails until its cleanup is recorded;
- unchanged identities pass regardless of duplicate occurrence counts.

Some currently baselined entries have `error` severity because
`drf-spectacular` cannot infer schemas for those views. The baseline records
existing debt; it does not assert that the affected endpoint is completely or
correctly represented. New entries of either severity remain blocked.

## Generated investigation artifacts

Every CI run that reaches the OpenAPI step uploads
`openapi-generation-py3.12` containing:

- `schema.generated.yaml`;
- `diagnostics.generated.json`.

The upload runs even when the gate fails, so a schema diff or diagnostic change
can be inspected without reproducing Linux locally. Generated files under
`artifacts/` and the default local output files are ignored by Git.

## Updating reviewed artifacts

Routine changes must first fix or test the underlying API change. Then regenerate
on canonical Linux with Python 3.12:

```bash
make openapi-write
make openapi-check
```

`make openapi-write` may:

- update the tracked schema;
- bootstrap a missing diagnostics baseline; or
- record diagnostic cleanup.

It refuses to grandfather a new diagnostic identity. Resolve or explicitly
annotate the source so drf-spectacular can describe it before updating the
baseline. The writer also refuses non-Linux and non-Python-3.12 environments.

### Initial bootstrap from CI

The initial baseline can be imported from an immutable Linux CI artifact on a
different development platform only through the guarded bootstrap mode:

```bash
PYTHONPATH= PYTHONHASHSEED=0 uv run --locked --group dev python scripts/check_openapi_schema.py \
  --bootstrap-schema-artifact artifacts/ci-bootstrap/schema.generated.yaml \
  --bootstrap-diagnostics-artifact artifacts/ci-bootstrap/diagnostics.generated.json
```

This mode is available only while both tracked artifacts are absent. It validates
the report's canonical serialization and policy fingerprint, regenerates the
schema twice locally, and requires exact schema, identity, and occurrence-total
parity before copying the schema and projecting a count-free baseline. It cannot
be combined with the normal write flags and cannot update an existing baseline.
The command validates artifact content, not GitHub provenance. Reviewers must
download both files from the immutable CI run for the exact candidate SHA and
verify the hashes printed by that run before importing them.

## Reviewing a schema change

Review at least:

1. `itambox/schema.yaml` for unexpected paths, methods, parameters, response
   shapes, security schemes, and component changes;
2. `scripts/openapi_diagnostics_baseline.json` for new debt or legitimate
   cleanup;
3. the generated diagnostics report when one source identity has many
   occurrences;
4. tests for the serializer/view behavior represented by the schema.

A stable schema is not proof that the API implementation is correct. It is a
deterministic contract diff and must be reviewed alongside runtime tests.
